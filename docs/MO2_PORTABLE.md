# Portable MO2 — verified mechanics

Answers open question **#5**. Written 2026-08-16 by dissecting a **real, working MO2 2.5.2
instance** (`C:\Modding\mo2_sf`, Starfield) rather than by reading the wiki. Where a claim
comes from the wiki instead of that instance it is marked *(unverified here)*.

The instance dissected is the same MO2 version as the current release, so its layout is
current, not historical.

---

## 1. Which MO2, and where from

**MO2 2.5.2** — the latest release (tag `v2.5.2`, published 2024-08-04). The local
Starfield instance reports `version=2.5.2` in its `ModOrganizer.ini`, so what follows is a
description of the current release, not an old one.

Two assets matter on the GitHub release:

| Asset | Use |
|---|---|
| `Mod.Organizer-2.5.2.7z` | **This one.** Archive, no installer, no registry writes — exactly what a portable instance wants. |
| `Mod.Organizer-2.5.2.exe` | Installer. Writes to Program Files and the registry. Avoid. |

**This is not on Nexus.** MO2 itself is fetched from GitHub releases, so the entire
bootstrap — MO2, plus F4SEVR from silverlock — happens before Nexus is involved at all.
See [`NEXUS_DOWNLOADS.md`](NEXUS_DOWNLOADS.md).

Note the hard floor: 2.5.x requires **Windows 10 1809+ or Windows 11** (Qt 6 / Python
3.11). Worth an explicit precondition check in the recipe rather than a confusing crash.

**FO4VR is natively supported.** `plugins/game_fallout4vr.dll` ships in the box, alongside
`game_fallout4.dll`, `game_skyrimvr.dll` and the rest. No manual game registration, no
third-party plugin. Open question #5's "does it need registering the game manually for VR?"
is answered: **no**.

---

## 2. What makes an instance portable

Two mechanisms, and they are not the same thing:

1. **`ModOrganizer.ini` sitting next to `ModOrganizer.exe`** is what makes the instance
   portable. A global instance keeps its ini in `%LOCALAPPDATA%\ModOrganizer\<InstanceName>\`
   instead. This is the real distinction.
2. **An empty `portable.txt`** in the same folder additionally *forces* portable mode and
   suppresses the instance-manager dialog at startup. *(Wiki-sourced; the dissected instance
   does not contain a `portable.txt`, and is portable regardless — consistent with #1 being
   the mechanism and #2 being a UI suppressor.)*

The recipe should write **both**: the ini because it is required, `portable.txt` because an
agent driving MO2 must not be handed a modal dialog.

## 3. Directory layout

Everything lives under the MO2 folder. From the real instance:

```
<instance>/
  ModOrganizer.exe
  ModOrganizer.ini          <- portability marker + all settings
  portable.txt              <- (add this) empty, suppresses instance manager
  mods/
    <Mod Name>/             <- one dir per mod, name is the display name
      meta.ini              <- provenance (see §5)
      <data files>          <- laid out as they appear under Data/
  profiles/
    Default/                <- see §4
  downloads/
    <archive>               <- plus a sibling <archive>.meta
  overwrite/                <- anything the game writes that no mod claims
  logs/  crashDumps/  plugins/  ...
```

`mods/<name>/` contents are **Data-relative**. A mod whose files go to
`Data/F4SE/Plugins/foo.dll` is stored as `mods/Foo/F4SE/Plugins/foo.dll`. This is the
single most important fact for generating an instance without driving the GUI: installing a
mod is, mechanically, *extract the archive to a directory with the right root*.

## 4. Profile files

`profiles/Default/` from the real instance, with what each does:

| File | Role | Generated by us? |
|---|---|---|
| `modlist.txt` | **Conflict priority.** `+Name` enabled, `-Name` disabled. **The FIRST line wins — highest priority at the top.** Verified by test, not assumed. | **Yes — this is the conflict-winner decision from the manifest.** |
| `plugins.txt` | Plugin activation. `*Name.esm` = active, bare name = present but inactive. | Yes |
| `loadorder.txt` | Plugin **order** (masters first). | Yes |
| `settings.ini` | `LocalSaves`, `LocalSettings`, `AutomaticArchiveInvalidation`. | Yes |
| `initweaks.ini` | Merged into the game ini at launch. Real instance holds just `[Archive] bInvalidateOlderFiles=1`. | Yes |
| `archives.txt` | BSA/BA2 load list. | Game-generated; leave alone |
| `lockedorder.txt` | Pinned plugin positions. Empty in practice. | Leave empty |
| `<Game>Custom.ini`, `<Game>Prefs.ini` | Per-profile game inis, **only when `LocalSettings=true`.** | See below |

### `modlist.txt` ordering — measured, and the first guess was wrong

**Verified 2026-08-16 by `core/tests/test-conflict-order.ps1`: the FIRST line of
`modlist.txt` wins a file conflict.** Two synthetic mods claiming the same
`Scripts/…probe.txt` were installed both ways round; the file read back from inside usvfs
followed whichever mod was listed first. No reversal is involved anywhere.

**This caught a real bug in this project's own spec.** The manifest's `order.install` is
written winner-first, and `MANIFEST_SCHEMA.md` instructed the writer to *reverse* it when
emitting `modlist.txt`. Since the file is also winner-first, that reversal would have handed
**every single conflict to the loser** — while installing cleanly, launching fine, and
looking correct. Precisely the failure this project exists to prevent, sitting in the
specification for it.

The lesson generalises past this one field. The claim "the file is bottom-up" came from
reading community docs and staring at a real instance, and it *sounded* authoritative enough
that it propagated into three files before anything executed it. **A conflict-order claim
cannot be verified by reading**, because both possibilities produce a plausible-looking
instance. It needed a test, and the test needed to be able to fail.

Run it after any change to instance generation:

```powershell
core\tests\test-conflict-order.ps1     # exit 0 pass, 1 fail, 2 inconclusive
```

It is headset-free and never launches the game — the probe is a PowerShell process run
inside usvfs, so it takes seconds and is CI-safe. Note it distinguishes **inconclusive**
(exit 2, the probe never ran) from **fail** (exit 1, order made no difference); after the
modal-dialog incident, "no result" must never be allowed to read as a pass.

### Local INIs — a decision the recipe must make

The dissected instance runs `profile_local_inis=false`, so it edits the *real*
`Documents\My Games\Starfield\` inis. For this project that is the wrong default:

- `LocalSettings=true` puts `Fallout4Custom.ini` **inside the profile**, so the agent's
  hardware-adaptive INI tuning is contained, versionable, and reversible by deleting a
  directory.
- With `false`, the agent edits the user's real inis — mutating state outside the instance
  it claims to own.

**Recommendation: `LocalSettings=true`.** It makes the adaptive half of the design (INI
tuning per GPU/headset) a first-class, undoable artifact instead of a side effect.
`LocalSaves` is the user's call; default `false` so saves stay where they expect.

## 5. `ModOrganizer.ini` — the minimum

Stripped from the real file to what actually matters. Everything else (`[Geometry]`,
`[Servers]`, `[recentDirectories]`) is UI state MO2 regenerates.

```ini
[General]
gameName=Fallout 4 VR
selected_profile=@ByteArray(Default)
gamePath=@ByteArray(C:\\Program Files (x86)\\Steam\\steamapps\\common\\Fallout 4 VR)
version=2.5.2
first_start=false

[Settings]
profile_local_inis=true
profile_local_saves=false
profile_archive_invalidation=true

[customExecutables]
size=1
1\title=F4SEVR
1\binary=C:/Program Files (x86)/Steam/steamapps/common/Fallout 4 VR/f4sevr_loader.exe
1\workingDirectory=C:/Program Files (x86)/Steam/steamapps/common/Fallout 4 VR
1\arguments=
1\hide=false
1\ownicon=true
1\steamAppID=
1\toolbar=false
```

Three encoding traps, all observed in the real file:

1. **`@ByteArray(...)`** wraps `selected_profile` and `gamePath`. Qt serialisation. Write it
   or MO2 will not read the value.
2. **Backslashes are doubled inside `@ByteArray`** (`C:\\Program Files...`) but
   `[customExecutables]` paths use **forward slashes** and are not wrapped. The same path is
   spelled two different ways in one file. A naive writer gets this wrong.
3. **`gameName` is the MO2 game name**, not a folder name — `Fallout 4 VR` for FO4VR
   (the Starfield instance uses `Starfield`). *(Exact FO4VR spelling is inferred from the
   plugin naming and Starfield's pattern — **verify on first run**; it is one string and
   getting it wrong is a loud, immediate failure, not a silent one.)*

`first_start=false` suppresses the setup tutorial. Another modal an agent must not meet.

### Absolute paths are baked in — a real portability limit

The dissected instance still carries `H:/mo2_sf/explorer++/Explorer++.exe` in
`[customExecutables]` after being moved to `C:\Modding\mo2_sf`, and a `gamePath` under
`C:/Program Files (x86)/Steam` alongside a stale `C:/Steam/...` executable entry. "Portable"
means *self-contained*, **not** *relocatable*. Moving an instance leaves dangling absolute
paths behind.

Implication for the recipe: paths are **generated per machine, every time** — never copied
from a reference instance, and never committed. This is precisely the deterministic/adaptive
split the README describes, showing up in the file format itself.

## 6. `mods/<name>/meta.ini` — provenance, and a manifest gift

Real example, `mods/Address Library for SFSE Plugins/meta.ini`, trimmed:

```ini
[General]
gameName=Starfield
modid=3256
version=20.0.0.0
installationFile=All in one - v20 (...) SFSE Address Library-3256-20-1775643723.zip
repository=Nexus
nexusFileStatus=1

[installedFiles]
size=1
1\modid=3256
1\fileid=61900
```

**`(modid, fileid)` is exactly the pin the manifest needs.** It uniquely identifies one
uploaded file of one mod, it is what Nexus's own API and `nxm://` links address, and MO2
writes and reads it natively. So the manifest's identity fields are not an invention of this
project — they are MO2's own, which means a generated instance is indistinguishable from a
hand-built one and MO2's update checking keeps working.

`meta.ini` also carries a cached `nexusDescription` blob. Skip it; it is a cache, not state.

## 7. Downloads and the archive name

`downloads/<archive>` with a sibling `<archive>.meta`. The archive filename is Nexus's own
and is itself structured:

```
All in one - v20 (1.16.236.0) SFSE Address Library-3256-20-1775643723.zip
                                                   ^^^^ ^^ ^^^^^^^^^^
                                                  modid ver  timestamp
```

The `.meta` holds the CDN URLs, and **those URLs contain the file's MD5**:

```
https://cf-files.nexusmods.com/cdn/4187/3256/<file>.zip?md5=TvWPBthkjbp5nQCaVVSeOw&expires=...&user_id=...
```

That is base64'd MD5. Useful for cross-checking a download, but **not** a substitute for the
manifest's own hash: the URL is signed, user-scoped, and expires — it is a fact about one
download event, not about the file. Hash the bytes on disk.

## 8. Can MO2 be driven headlessly?

Open question #5 asked. **Partly, and the useful part is a "no, and it doesn't matter":**

- **Building the instance needs no GUI at all.** Every artifact above is a text file in a
  known place, and mod installation is archive extraction into `mods/<name>/`. The agent
  writes the instance directly. This sidesteps FOMOD scripting for any mod whose archive is
  already Data-relative.
- **Launching the game does need MO2's process**, because the whole point is usvfs — the
  virtual file system that makes `mods/` appear as `Data/`. That is
  `ModOrganizer.exe -p "Default" "moshortcut://:F4SEVR"` *(command-line form is
  wiki-sourced and **unverified** — confirm on first run)*.

The practical consequence is good news: **the agent never has to click through MO2's UI**,
and FOMOD installers reduce from "the agent must make GUI choices" to "the agent must place
files correctly" — which the manifest can specify as data.

## What remains unverified

**Closed 2026-08-16** by building a real portable FO4VR instance at `C:\Modding\mo2_fo4vr`
and launching the game through it. See [`VERIFICATION.md`](VERIFICATION.md) for the run.

- [x] **`gameName` for FO4VR is `Fallout 4 VR`** — confirmed twice: the literal string is in
      `plugins/game_fallout4vr.dll`, and MO2 logged
      `using game plugin 'Fallout 4 VR' ('Fallout4VR', variant (none), steam id '611660')`.
      `Fallout4VR` (no spaces) is the *short* name, used for `--game=` and the Documents
      folder. Two different strings; do not mix them up.
- [x] **`portable.txt` works on 2.5.2.** MO2 reported the instance as `Portable` and never
      showed the instance manager.
- [x] **`moshortcut://` syntax confirmed**:
      `ModOrganizer.exe -p Default "moshortcut://:<Title>"`.
      **Give custom executables titles with no spaces.** A title of `Fallout 4 VR (vanilla)`
      was split on whitespace by the caller and MO2 reported
      `Executable 'Fallout' does not exist in instance 'Portable'`. Renaming to `Vanilla`
      fixed it. The recipe should generate space-free titles as a rule.
- [x] **Hand-written `ModOrganizer.ini` survives.** MO2 *augments* rather than clobbers: it
      kept both of our `[customExecutables]` entries and appended its own auto-detected ones
      plus `[PluginPersistance]` and `[recentDirectories]`. Generating the ini by hand is a
      supported workflow, not a hack.
- [x] **FO4VR ini names are the flat-Fallout ones** — `Fallout4.ini`, `Fallout4Custom.ini`,
      `Fallout4Prefs.ini` (verified in the plugin binary), living under
      `Documents\My Games\Fallout4VR\`. **Not** `Fallout4VR*.ini`.
- [x] **`LocalSettings=true` works and is the right default.** MO2 used the profile's inis
      and wrote window position back into `profiles/Default/Fallout4Custom.ini` rather than
      touching the user's Documents.
- [x] **Virtualisation verified in both directions.** `devbench.dll` existed *only* in
      `mods/devbench/F4SE/Plugins/`, and F4SEVR found it at
      `...\Fallout 4 VR\Data\F4SE\Plugins\devbench.dll`. Writes went the other way: the
      plugin's `config.json` and `runtime.json` landed in `overwrite/F4SE/Plugins/devbench/`.
      **The game's real `Data/` is still byte-for-byte vanilla.**
- [ ] FOMOD archives whose root is *not* Data-relative — still open; none of the mods
      installed so far needed it.
- [ ] Whether MO2 can install from an archive without the GUI (we placed directories
      directly, which worked, but never exercised MO2's own installer).

## Two things that will bite an unattended agent

**1. A missing dependency can produce a modal dialog, not an error code.** With the VR
Address Library absent, `devbench.dll` popped a Windows message box —
`REL/IDDB.cpp(82): failed to open: Data/F4SE/Plugins/version-1-2-72-0.csv` — and the process
sat there. From outside it looked like a silent hang: no crash in the event log, no further
log lines, nothing on stdout. An agent polling for a result would have waited forever and
then reported something false.

Mitigations the recipe needs: **verify declared dependency files exist before launching**
(cheap, and would have caught this one), impose a **launch timeout**, and treat "no response
and no crash" as *inconclusive*, never as failure-with-a-cause.

**2. MO2 logs almost nothing about spawning.** `mo_interface.log` ends at
`not saving lists during directory update` whether the launch succeeded or not. Do not parse
MO2's log for launch success — watch for the game process and the acceptance signal instead.

## Warning worth surfacing to the user

MO2 logs, on every start:

> `the game is in Program Files; this may cause issues because it's a special system folder`

FO4VR is in the default Steam library under `C:\Program Files (x86)`. It did not cause a
problem in this run, but it is a known source of permission weirdness in Creation Engine
modding. The recipe should surface this once, as a note, and not pretend it is fatal.
